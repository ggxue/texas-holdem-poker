# 筹码与未完成牌局持久化研究

> 2026-10-08范围更新：数据库、跨重启存档和恢复要求已撤销，改为内存及重新入房设100；本文件保留历史研究/范围，不授权旧存档实施。当前见[memory-reset-decision.md](memory-reset-decision.md)。

现行存档/恢复行为已固化到 [正式规格](spec.md) 的 D7–D8，验收见 AC33–AC40。
本研究保留调研时的建议和待决讨论，不能据此覆盖已确认规则；表结构与锁方案仍是实现参考。

- 查阅日期：2026-10-08（Asia/Singapore）。状态：研究完成，Q26 核心存档与恢复行为已获用户确认；具体决定见[需求讨论记录](requirements-discussion.md)。研究中的字段、表与锁设计仍是实现建议，不代表已完成设计或验证。
- 已阅读当前需求和[免费云研究](free-cloud-research.md)。采用已简化的单房间玩法：底注 1、每轮最多一次固定 10 下注、无加注、单池实际投入不退、全押者可争整个池；机器人只过牌/跟注，零余额仅新局前补 100；持久 Cookie 身份、新页面接管、房主逐局手动开始。
- Q25 已获用户确认（研究开始时需求文件仍等待主代理写入）：正常断线保留 30 秒，到期离房并弃牌（包括全押）；行动期限 30 秒，超时能过牌则过牌，否则弃牌；重连不重置原行动期限；有人处于断线宽限时不开新局。该规则尚未决定平台故障的计时例外。
- 只研究外部 PostgreSQL 一种简单方式，不注册、部署或实现，不提前选定 Neon/Render。

## 结论与方案比较

**推荐提案：每次有效变更将余额、房间和当前牌局一起提交到外部 PostgreSQL；应用重启后读取最后提交的完整状态。** 单房间最多三位参赛者，保存一份小型快照加余额记录，比补做异常退款/作废规则更直观。此为项目判断，数据库提供的是事务能力，不是现成的扑克恢复功能。[PostgreSQL 事务](https://www.postgresql.org/docs/current/tutorial-transactions.html)

| 方案 | 对本项目的结果 | 判断 |
| --- | --- | --- |
| 仅保存余额，每次下注已扣款 | 崩溃后仍能读余额，但无法凭余额知道底池、赢家资格、牌、轮到谁；清空牌桌会使未结算投入失去去向 | 不推荐；要额外保存托管/投入记录及作废处理，本质上仍需牌局状态 |
| 仅保存上局结算余额，下注全在内存 | 崩溃后回到上局余额；表现为本局已下注被撤回，或者未确认变更丢失 | 只有用户明确接受异常作废/退款才成立，不能从“退出不退款”推定 |
| 余额 + 当前房间/牌局快照原子保存 | 重启读取同一版本的余额、底池与参赛状态；可以继续处理已存在的牌局 | 推荐；仍可能因已过期的计时而立即自动过牌、弃牌或结算，并非回到原操作画面继续计满 30 秒 |

以上为项目推断。数据库提交多项变更可以做到全部成功或全部回滚，但不能凭空恢复没有持久化的数据。[PostgreSQL 事务](https://www.postgresql.org/docs/current/tutorial-transactions.html)

## 已核实的官方事实

- PostgreSQL 事务可将多条修改组合为原子操作，未完成状态对其他事务不可见；`BEGIN`/`COMMIT` 或事务 API 是多条语句成为一个整体的前提。[Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html)
- PostgreSQL 的异步提交设置 `synchronous_commit=off` 可能使已报告成功的最近事务在故障后丢失。筹码路径不应为了性能自行关闭同步提交；实际托管数据库设置需在部署验证时检查。[WAL 配置](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT)
- Neon 官方当前架构说明：计算与持久存储分离，提交在 safekeepers 法定多数确认 WAL 后向客户端报告成功；计算节点停止不等于删除持久数据。该架构说明不是 Free 的无条件可用性或永不丢数据承诺。[Neon 存储架构](https://neon.com/blog/wal-s3-lakebase-storage-for-the-era-of-agents)
- Neon Free 闲置 5 分钟停止计算；计算/公网传输额度用尽会暂停到下计费周期，存储超限会导致增长存储的操作失败，官方明确这些额度限制不删除数据。[Neon Plans](https://neon.com/docs/introduction/plans#what-happens-if-i-exceed-my-free-plan-limits)
- Render Free 本地修改在重启、重部署、休眠后丢失；唤醒通常约一分钟，因此临时磁盘不能保存权威快照，一分钟也可能超过已确认的 30 秒期限。[Render Free](https://render.com/docs/free)
- Render 部署会先启动新实例，再切换流量，旧实例随后才退出；Free 单实例规格不等于两个应用进程从不短暂重叠。旧 WebSocket 也不能直接迁移到新进程。[Deploys](https://render.com/docs/deploys#zero-downtime-deploys)、[WebSockets](https://render.com/docs/websocket)
- PostgreSQL 有 `transaction_resolution_unknown` 错误条件。网络断开或提交响应遗失时，应用不能把“没收到成功”一律解释成“数据库已经回滚”。[官方错误码](https://www.postgresql.org/docs/current/errcodes-appendix.html)

## 最小保存范围与提交时点（项目提案）

建议使用少量表：玩家身份与整数余额、一行单房间快照、一张已处理请求记录。快照可用 PostgreSQL `jsonb`，但具体字段仍由 spec/实现设计确定；不引入事件总线、Redis 或完整事件溯源。[JSON 类型](https://www.postgresql.org/docs/current/datatype-json.html)

快照至少应含：房间座位的身份、入房先后及房主；当前 hand ID/状态；本局固定参赛身份（与新占座者区分）；已洗好的剩余牌序、手牌、公共牌、阶段；各人投入、弃牌/全押状态、底池；本轮目标与唯一主动下注是否已用、当前行动人；行动绝对截止时间、已观测断线的绝对截止时间；是否已结算、结果与版本。重启不重新洗牌，也不把旧参赛者的牌交给同座位新玩家。

所有影响权威状态的事件都须同一事务保存：初始发 100、开始新局/归零补给/底注、下注与跟注、过牌/弃牌、自动超时、牌局推进、结算、入房/离房/房主交接和页面接管。只在局末保存不能满足“途中重启还原最后有效动作”。可先计算候选状态，事务提交成功后再更新内存与广播；WebSocket 没送达时客户端重新读已提交状态，不能反向撤销提交。

例如余额 99 的玩家跟注 10：保存后的余额 89、底池增加 10、玩家投入与轮到下一人必须在同一提交中出现。结算时发奖、清池和标记 settled 也要同一提交；不能先发钱后写“已结算”。初始发放/新局补给须有稳定身份与 hand ID 保护，不能把恢复当作新玩家或新开局。

## 提交结果不明、重复请求和旧进程（项目提案）

1. 每个命令带稳定 request ID、身份、hand ID/轮次及预期状态版本；重试沿用同一 ID。已处理 ID 有唯一约束，在修改余额和快照的同一事务记录请求内容摘要与结果。相同 ID 不同内容拒绝，避免把另一条指令误当成重试。[唯一约束与冲突处理能力](https://www.postgresql.org/docs/current/sql-insert.html)
2. 对唯一房间行用短事务 `SELECT ... FOR UPDATE` 串行化修改，并读当前已提交版本再验证动作。不要持锁等待玩家 30 秒。所有权威写路径遵循同一锁顺序；只用 Go 内存锁不能约束部署中的另一进程。[PostgreSQL 行锁](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)
3. `COMMIT` 超时/断线后暂不发成功或再次扣款。重新连接同一主写数据库，先取得同一房间锁再核查 request ID，避免在原事务仍在提交时，单次无锁查询“未找到”就重复执行。找到则返回已提交结果；确认原事务已结束且没有记录后，才对相同 ID 重新验证执行。数据库仍不可访问时保持“结果待确认”。
4. 房间写版本防止旧快照覆盖；再保存应用所有者 generation/epoch。新进程接管须在数据库事务内变更 epoch；旧进程每次写都须验证自己仍是所有者，失效则停止动作/计时并关闭其连接，不能重读后自动抢回。仅版本冲突后无限重试不构成对旧进程的隔离。实际健康检查/接管顺序要在实现票据验证，避免新部署失败后把仍在线旧服务永久隔离。[Render 实例重叠依据](https://render.com/docs/deploys#zero-downtime-deploys)、[PostgreSQL 行锁能力](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)

以上是利用数据库能力设计的项目方案，官方不自动提供请求去重或扑克 exactly-once。未正确覆盖计时器、机器人、离房等所有写路径，仍可能重复执行。

## 不可用与恢复时限（项目提案及待决事项）

数据库唤醒、故障、限额暂停或写失败期间，停止会改变状态的动作：不在内存里继续扣款、发牌、结算、补给或确认离房后宣称成功；界面显示“连接/存档恢复中”，拒绝新开局。允许展示最后确认快照但标明可能过时。数据库恢复后先解决结果不明请求，再从已提交版本恢复，不能直接用旧内存继续。

保存绝对截止时间，重启/重连不把已经存在的行动倒计时重置成 30 秒。已有 disconnect deadline 同样不重置。启动时已过期的事件按确定顺序、事务和去重规则处理，可能很快结束本局；这需要用户理解“恢复牌局”包含自动结果，并不保证恢复原行动机会。

研究时尚待确认的故障边界（现行行为以已确认 Q26 为准）：

- 应用崩溃前未观察到断线的玩家，没有可靠的已保存断线起点。恢复时是否给予新的 30 秒连接恢复宽限，还是根据另存的故障/连接证据判定，必须明确；不能假装知道进程死亡瞬间，也不能直接把所有旧记录当在线。
- 已创建 deadline 保留；停机期间尚未创建的后续行动，从何时开始 30 秒应明确。建议只处理已存在的过期事件，后续新行动机会从实际恢复推进时起算，不凭空补造停机期间的所有回合。此为行为提案，不是 Q25 已确认规则。
- 同时到期的行动超时与离房处理顺序、恢复时新页面接管的权限代际、暂无真人时怎么恢复房主，需纳入可观察验收；不能在无法保存时先执行离房/发奖。
- 快照损坏、未知版本或资金不变量不成立时，建议停在故障状态等待处理，不猜赢家、清池、退款或重发 100。具体人工恢复方式未确认。

推荐先确认“余额与未完成牌局共同保存并恢复；保存失败则停止变更”的核心策略，再明确平台故障与计时的上述例外。不要把接受 Q26 解释成保证零停机、永不丢失或无限历史恢复。

## 建议验收边界

这是针对实际可见结果的建议，尚非测试实现：

- 跟注提交前/后分别杀进程：恢复后只出现完整旧状态或完整新状态，余额与底池不脱节。
- 提交成功但响应遗失：同 request ID 重试仅扣一次、结算仅派奖一次、补给仅发生一次。
- 恢复已结算局/尚未结算局：前者不再派奖，后者保留牌序、投入、身份和原期限。
- 数据库不可用：机器人和自动计时事件也不继续产生未提交变更；恢复后再确定权威结果。
- 模拟部署两进程及旧页面迟到消息：旧 epoch/控制代际不能写入；新进程读取最新版本。
- 恢复耗时超过 30 秒：既存期限不能被重启抹掉；按最终确认的故障宽限规则处理，底池不消失。

实际云账号、数据库持久配置、版本兼容性、空间额度与部署过程仍需实测；本研究不等同于通过这些验收。
